## 五、质量与安全基线（答辩速查）

- 生产构建：`tsc --noEmit` 零错误、`next build` 全绿、vitest 29 例单测全过
- 引用硬约束：AI 输出仅允许引用检索列表内诗篇，`citationCheck` 逐条校验，闭环实验引用越界 0/16、归因率 93.8%
- 接口治理：AI 接口按成本分档限流（10~2 次/分钟）、登录/注册/MCP 限流防刷、全局错误边界、SSE 中断可停
- AI 安全：输入/输出双向内容过滤 + 违规兜底（`lib/content-filter.ts`）——输入侧拦截 prompt injection / 越狱、色情低俗、血腥暴力、仇恨歧视、违法交易并返回 400；注解 / 风格迁移 / AI 助手输出侧按最近 2000 字滚动校验，命中即中断 SSE 并回传安全提示；按明确违规语境匹配，正常古诗词字词不误杀
- 格律后校验（`lib/meter.ts`，自研算法）：风格迁移生成后按**中华新韵**校验押韵与平仄（律绝查偶数句同韵部 + 末字平仄硬规则 + 二四六交替软规则，一三五不论、首句入韵宽容；词按词牌韵脚查押韵），违规详情注入重写 prompt（计入 4 次上限），前端展示 ✓/⚠ 格律徽章；读音数据由 `scripts/gen_xinyun_data.py`（pypinyin）构建期生成，覆盖 4.2 万字、138KB，运行时零依赖
- 无障碍：`prefers-reduced-motion` 全动画降级、打字机 aria-label、键盘可达
- 权限边界（RBAC）：`users.role` 取 `user`（默认）/ `admin` / `disabled`；管理后台采用「页面级 + 接口级 + 会话级」三层校验，六个 `/api/admin/*` 路由逐一调用 `requireAdmin()`，前端 `components/workbench/shell.tsx` 按 `user.role === 'admin'` 条件渲染后台入口。`middleware.ts` matcher 覆盖 `/workbench`、`/profile`，`/admin` 由 `app/admin/layout.tsx` 承担服务端重定向，两条路径互不依赖；会话 `role` 由 `jwt` 回调实时查库，非注册时写死

### 5.2 内容审核状态机与作者撤回权

学习社区不是「发帖即可见」，而是先审后发的闭环。状态机为前后端共享纯函数 `lib/postWorkflow.ts`，避免两端判断不一致：

| 状态 | 可见范围 | 触发 | 作者权限 |
| --- | --- | --- | --- |
| `pending` | 作者 + 管理员 | 普通用户发帖 / 命中敏感词（含管理员） | 撤回申请 |
| `approved` | 全体成员 | 管理员通过 / 管理员发布免审 | 撤回帖子 |
| `rejected` | 作者 + 管理员 | 管理员拒绝，`review_note` 回显作者 | 撤回投稿 |
| `withdrawn` | 作者 + 管理员 | 作者撤回（终态） | 不可再审批，仅管理员可删除 |

工程要点三条：

1. **数据可见性由服务端收口**：`GET /api/posts` 只返回 `status='approved'` 的全量帖子与 `user_id=本人` 的非公开投稿；审核备注 `review_note` 也只对作者本人返回。评论与点赞接口统一校验 `status='approved'`。
2. **实时同步**：`hooks/useAutoRefresh.ts` 在标签页可见时按间隔轮询（用户端 / 审核页 5 秒、总览 10 秒），请求带 `cache: 'no-store'`，切回标签页立即补同步；用户端比对状态快照后主动提示审批结果。不做 SSE 是因为审核状态无需跨进程事件总线，轮询在换机复现时更简单。
3. **并发安全（撤回优先）**：作者撤回与管理端审批都用 Prisma 条件更新（`status != 'withdrawn'`），以先落库者为准；撤回接口先校验 `user_id` 归属，普通用户与管理员都只能撤回自己的投稿。管理端列表的 `status` 参数走白名单，非法值回落 `pending`，避免越权拿到全表。

### 5.3 管理后台：可操作模块与运行时配置

后台六个页面没有静态占位卡片，每个数字都对应可查询、可操作的数据：

| 模块 | 操作 | 实现要点 |
| --- | --- | --- |
| 总览 | 待审帖子行内通过、指标卡跳转、待回复反馈摘要 | `GET /api/admin/stats` 补 `recentFeedback`；10 秒 `no-store` 同步 |
| 用户 | 角色 / 状态变更 + 详情弹窗 | `GET /api/admin/users/[id]` 现查 `posts / comments / creations / favorites / feedbacks` 计数与最近投稿 |
| 诗词 | 增删改查 | 注解、意象关联随外键级联删除 |
| 帖子 | 通过 / 拒绝 / 删除，四态分栏 | 见 5.2 |
| 反馈 | 回复 / 修改回复 / 重新打开 / 删除 | `PUT /api/admin/feedback` 的 `action` 白名单；用户端「帮助与反馈」10 秒轮询 |
| 分类 | 意象增删、重算关联数、社区分类增删改与恢复默认 | 见下 |
| 侧栏 | 待审 / 待回复角标、退出登录 | 与总览同源轮询，评审切换双账号无需绕路 |

**社区分类改为运行时配置**：`data/post-categories.json`（`{ id, name, desc }`）由 `lib/postCategories.ts` 读写，异常时回落内置四项；`validateCategories()` 做名称唯一、长度与数量校验并配单测。管理员保存整份清单时，`PUT /api/admin/post-categories` 按稳定 `id` 做 diff：名称变化用 `prisma.post.updateMany` 迁移历史帖子的 `category` 字符串，被删分类先 `count` 检查占用、有帖子则 400 拒绝，避免历史帖子「掉分类」。`GET /api/posts` 筛选与 `POST /api/posts` 校验都改为 `isPostCategory()` 动态读取；用户端 `study-square.tsx` 从 `GET /api/post-categories` 拉取选项，5 秒轮询同步，选中分类被删时自动回落。选择配置文件而非新增数据库表，是为了让评审环境仅导入既有 `ai_poetry.sql` 即可运行，不引入额外迁移。

意象计数重算用单条相关子查询 `UPDATE imagery SET count = (SELECT COUNT(*) FROM poem_imagery WHERE ...)`，避免数千条逐行 `update` 撑爆事务；语句为静态常量、无外部输入。
